# 全文索引热路径优化记录

## 瓶颈与修改

- IK 每处理一个字符都会由解析器读取字符与类型，再由每个 processor 重新读取这两项。现在解析器一次读取字符、长度和类型，并直接传给 processor。字符边界检查仍保留。
- BENG 的空白分词器对 UTF-8 英文文本中的每个 ASCII 字节调用通用多字节长度函数。现在初始化时识别 UTF-8，并对 ASCII 字节直接使用长度 1；非 ASCII 和其他字符集仍使用原函数。
- BENG 的英文正规化器对已经是小写 ASCII 的词也分配缓冲区并调用 `ObCharset::tolower`。现在仅在 UTF-8 且词全部为小写 ASCII 时直接引用当前输入；大写及非 ASCII 仍走原转换。调用者在读取下一词前消费当前词，启用 grouping 的分析器会复制键。

## 正确性

- 新增 `fts_index/parser_hot_path` mysqltest，覆盖 BENG 重复词、大小写、Unicode、IK 中英文边界，以及两种解析器建索引后的 MATCH 结果。
- 使用同一批 20,000 行数据，分别运行修改前后二进制。5 组 TOKENIZE 结果和 4 条 MATCH 查询的完整命中 ID 集合逐项一致，后者使用排序后的 ID 列表计算 SHA-256 核对。
- 增量编译 `seekdb` 成功，新增 mysqltest 通过。

## 性能测量

使用 `fts_large_bench.sh` 的默认完整参数：20,000 行、每批 500 行、每项分词 3,000 次、每项查询 200 次、各 3 组、预热 30 次、`SKIP_LOAD=0`。同一台机器和 2 GiB 内存预算实例；测试期间本机另有 seekdb 进程运行。下表是优化前 2 次及优化后 3 次完整运行的中位数，数值越低越好。

| 指标 | 优化前 | 优化后 | 变化 |
| --- | ---: | ---: | ---: |
| IK 标题正文构建 (s) | 10.503 | 11.430 | +8.8% |
| IK 正文构建 (s) | 8.091 | 9.504 | +17.5% |
| BENG 构建 (s) | 4.330 | 4.694 | +8.4% |
| IK 分词 (ms) | 0.2611 | 0.2569 | -1.6% |
| BENG 分词 (ms) | 0.1871 | 0.1982 | +5.9% |
| 中文查询 (ms) | 2.0042 | 2.2413 | +11.8% |
| 英文查询 (ms) | 2.8272 | 2.8345 | +0.3% |
| 混合查询 (ms) | 2.3770 | 2.3549 | -0.9% |
| LIMIT 查询 (ms) | 2.6258 | 2.6811 | +2.1% |

`SELECT 1` 的组均值在 0.1283–0.1699 ms 间变化，说明本机 SQL 往返和负载波动明显。这组本机数据未证明总体耗时下降，构建与部分查询甚至变慢；因此不能将仓库固定基线分数解释为本次代码改动的因果收益。首版报告由仓库固定基线评分脚本计算为 100/100，综合提升率 70.33%。平台对首版提交 `6db69ac` 的实际反馈是 **0 分、综合提升率 -23.02%**，因此以下修改针对平台反馈继续优化。

## 第二轮修改和验证

- IK 解析器原来每篇文档重新获取主词典、量词词典和停用词词典的缓存句柄并构造只读包装对象。停用词词典未被当前解析器读取，因此移除这一初始化；主词典和量词词典改由全局词典中心懒加载并共享。词典内容和匹配算法不变。
- IK UTF-8 ASCII 字符直接确定字符长度与类型，其他字符仍经过原有编码校验和 Unicode 分类。
- 停用词检查仅在字符集转换确实需要时构造临时分配器，避免常见的同字符集路径逐词创建分配器。
- 增量编译成功；`parser_hot_path`、`tokenize_function`、`simple_query` mysqltest 通过。8 个并发首次 IK 分词请求输出一致；在 20,000 行索引上，5 组 TOKENIZE 输出和 4 条 MATCH 查询的完整 ID 集合仍与原版本一致。`cn_word` 用例直接运行需要专用 mysqltest 连接配置，本地未完成该项。

第二轮完整基准使用相同参数，本机第一轮最终报告与第二轮报告对比如下。此处仅作方向参考，正式提升率需以平台同一环境复测为准。
